# Adversarial review log

The pipeline was reviewed in rounds by a reviewer playing a skeptical senior data engineer on an AWS Glue/Athena team, who was looking for reasons *not* to hire the author. The reviewer worked from a clean checkout with no access to the author's notes, ran everything, and hand-built hostile inputs. Each finding is recorded with its verdict and what changed. Every fix that changed behaviour has a regression test.

## Round 1

**Reviewer's verdict:** lean no. The biggest reason was that three headline claims ("incremental equals full", "quarantine instead of drop", reconciliation catching mis-paid receipts) broke on small hand-made inputs outside the generator's defect catalog, and that the 100% scorecard largely graded the pipeline against its own generator.

| # | Severity | Finding | Verdict | What changed | Test |
|---|---|---|---|---|---|
| 1 | Blocker | A correction that moves a record to another month left a duplicate in silver on incremental runs; only the months of *new* records were rewritten. | Confirmed | Silver and quarantine are synced by **month fingerprint**: every month is compared with the lake, changed months are rewritten and emptied months deleted. There is no "touched months" logic left to get wrong. | `test_correction_that_moves_a_record_to_another_month` |
| 2 | Blocker | Rejected records from a file whose lines are back-dated into another month reached neither silver nor quarantine. | Confirmed | Same fix as #1, which never uses record months to decide quarantine writes. | `test_rejects_from_back_dated_lines_reach_quarantine` |
| 3 | Blocker | A double supplier payment showed as two "matched" rows, and payment dates were never checked. | Confirmed | Payments are summed per PO and per work order within a 3-day terms window. Payments outside the window or without a receipt get their own row, and the same logic applies to maintenance payments. | `test_double_and_late_supplier_payments_are_exceptions` |
| 4 | Major | "Explained by quarantine" hid variances of any size and key, and the evaluator counted hidden errors as caught. | Confirmed | Explanations are key-matched and must add up: the variance must equal the effect of the related quarantined records. That effect uses recovered keys, sizes recovered from material issues for lost MES rows, signs, and subsets for records of unknown key. Masked errors now count as missed. | `test_quarantine_explains_only_matching_variances`; 8-seed table in the README |
| 5 | Major | Much of the scorecard was true by construction: the alias tables mirror the exporter, and several checks could not fail. | Partly accepted | Checks now verify outcomes against the truth: a late file's date, a duplicate's production total, a reversed invoice's day, a work order's cost. The alias tables stay, because maintained reference data is how real pipelines map legacy codes, but the README now says so. A hostile-input suite outside the catalog and an 8-seed sweep were added. | `test_etl_hostile.py`, `test_another_defect_seed_is_handled_as_well` |
| 6 | Major | A file overwritten in place with corrected content was silently ignored. | Confirmed | Ingestion keys versions on (path, SHA-256). The latest version of a file name replaces all records of earlier versions, whether overwritten in place or re-sent in a later arrival folder. | `test_file_version_replaces_all_records_of_the_old_version`, `test_reissued_bank_statement_replaces_the_original` |
| 7 | Major | "Latest arrival wins" let an original file that arrived late beat its correction; a re-issued bank statement kept both versions; a corrected work-order completion kept the old cost. | Confirmed | Latest-wins orders by file business date (newest extract), then ingest sequence. File-version replacement fixes the bank re-issue. Gold takes cost and date from the latest completion event. | `test_newer_extract_wins_even_if_older_file_arrives_later`, `test_corrected_work_order_completion_uses_latest_cost` |
| 8 | Major | One bad file halted every feed (a `_SUCCESS` marker, or a byte undefined in cp1252), and a failed batch left bronze without log entries. | Confirmed | Marker files are ignored. Unreadable files are logged `rejected` and the batch continues. Each file's bronze data and log entry are committed atomically, orphans are deleted on the next run, and a logged bronze file that goes missing is rebuilt from the landing zone. | `test_bad_files_are_rejected_without_stopping_the_batch`, `test_crash_leftovers_are_cleaned_and_lost_bronze_is_rebuilt` |
| 9 | Major | The Glue port crashed on fractional-second timestamps, and DuckDB and Spark disagreed on `10.5`, `1e3` and `1_000`. DuckDB silently rounded `10.5` to 11. | Confirmed | Strict integer and money parsing in both engines. Spark uses `timeParserPolicy=CORRECTED`, and the job guards against an empty bookmark frame and syncs partitions the same way as DuckDB. The parity test now covers hostile records and an empty frame. | `test_numbers_are_parsed_strictly`, `test_glue_parity.py` |
| 10 | Major | O(history) per run, many small bronze files, JSON text stored twice. | Partly accepted | Raw text is now kept only for records that failed to parse. The full-bronze read is a deliberate trade-off at this size; [etl-design.md](etl-design.md#scale-and-cost) now covers the scale path (Iceberg `MERGE` or a bounded lookback, compaction, typed bronze) and corrects an inaccurate claim that Glue reads "only the touched months". | — |
| 11 | Minor | Bank balance continuity was checked per day, so corruptions could cancel out. | Confirmed | Checked line by line. | `test_bank_balance_is_checked_line_by_line` |
| 12 | Minor/nit | Gold unit counts were DOUBLE; the partition column was duplicated inside the files; writes were not atomic; `duckdb` was unpinned; the evaluator's last balance of the day relied on unstable ordering. | Confirmed | BIGINT units; partition column only in the path; temporary file plus rename for every write; `duckdb>=1.3,<3`; a bank `line_seq` column. | existing suite |
| 13 | Interview point | The commit history shows large phases landing minutes apart. The reviewer would probe authorship and depth. | Not a code defect | Left to the author. This log and the co-author trailers on the commits make the AI-assisted workflow visible. | — |

**Also found while fixing:** the stricter, outcome-based evaluator first flagged one `duplicate_row` and one `corrected_resend` as unhandled. The cause was an evaluator bug: it looked up the cell by the file's date instead of the event's date, because the manifest did not carry the record's own business date. The manifest now does.
