# Adversarial review log

The pipeline was reviewed in rounds by a reviewer playing a skeptical senior data engineer on an AWS Glue/Athena team, who was looking for reasons *not* to hire the author. The reviewer worked from a clean checkout with no access to the author's notes, ran everything, and hand-built hostile inputs. Each finding is recorded with its verdict and what changed. Every fix that changed behaviour has a regression test.

## Round 1

**Reviewer's verdict:** lean no. The biggest reason was that three headline claims ("incremental equals full", "quarantine instead of drop", reconciliation catching mis-paid receipts) broke on small hand-made inputs outside the generator's defect catalog, and that the 100% scorecard largely graded the pipeline against its own generator.

|---|---|---|---|---|---|

There is no "touched months" logic left to get wrong. | `test_correction_that_moves_a_record_to_another_month` |
| 2 | Blocker | Rejected records from a file whose lines are back-dated into another month reached neither silver nor quarantine. | Confirmed | Same fix as #1, which never uses record months to decide quarantine writes. | `test_rejects_from_back_dated_lines_reach_quarantine` |

**Also found while fixing:** the stricter, outcome-based evaluator first flagged one `duplicate_row` and one `corrected_resend` as unhandled. The cause was an evaluator bug: it looked up the cell by the file's date instead of the event's date, because the manifest did not carry the record's own business date. The manifest now does.

## Round 2

**Reviewer's verdict:** do not advance yet. The biggest reason was that reconciliation could mark a variance of any size as "explained by quarantine": one junk record on the right day was enough, and the evaluator only checked two of the seven checks for masking. The round-1 fixes held up under variations (incremental equals full across 28 random batch splits, strict parsing, month moves, failure isolation).

| # | Severity | Finding | Verdict | What changed | Test |
|---|---|---|---|---|---|
| 1 | Blocker | An unsized related quarantined record made any variance "explained". The `>12` candidate shortcut also explained everything. Quarantine was dated by its file, and a record that was later corrected and loaded still explained variances. | Confirmed | **New status `needs_review`:** an unsized record can no longer explain anything. Effects carry a direction (`+?`/`-?`), and a review needs the direction to fit and the variance to be within any bound on the unknown size (several lost MES rows are bounded by the station's issued-minus-produced gap). More than 12 candidates is review-or-exception, never explained. Quarantined records are dated by their own date and released once their key loads. Bank-line deposits and payments are recovered as sizes. | `test_unsized_quarantine_never_explains_and_is_bounded`, `test_unsized_quarantine_must_point_the_right_way`, `test_unknown_key_quarantine_explains_only_an_exact_match`, `test_quarantine_is_released_when_its_key_loads_later`, `test_quarantined_record_is_dated_by_its_own_date`, `test_quarantined_invoice_amount_explains_a_deposit_gap_exactly` |

## Round 3

**Reviewer's verdict:** do not advance. The biggest reason was that the reconciliation engine had become the riskiest part of the system: its rules for when quarantine "explains" a variance were hard to reason about, one quarantined record could explain two rows at once, and an unreferenced bank debit or a jump in a `BALANCE FORWARD` line was not flagged by any check. The reviewer also showed incremental and full runs disagreeing, and two ways to lose bronze data.

| # | Severity | Finding | Verdict | What changed | Test |
|---|---|---|---|---|---|
| 1 | Blocker | A 250,000 debit with no PO or WO reference, with consistent balances around it, raised nothing. Neither did a mid-year `BALANCE FORWARD` that jumped by 1,000,000. | Confirmed | New `unreferenced_bank_lines` check: every line must be a deposit or reference a PO or work order. Balance continuity now includes `BALANCE FORWARD` lines after the first. | `test_unreferenced_bank_debit_and_balance_jump_are_exceptions` |
| 2 | Blocker | A corrected extract that landed in the same arrival folder *after* a run, under a name that sorted first, won in the full run but not incrementally: ties were broken by discovery order. | Confirmed | Files carry an arrival time (their modification time; `LastModified` on S3). Records from different files are ordered by arrival folder, then arrival time, which no longer depends on when a run saw them. Versions of one file name stay ordered by arrival folder, then sequence: one folder holds one path per name, so its latest log entry is what is on disk. (Mutation testing caught a first version that also ordered versions by arrival time, which broke an in-place overwrite with an older timestamp.) | `test_same_day_extracts_are_ordered_by_arrival_time`, `test_overwrite_with_an_older_timestamp_is_the_current_version` |
| 3 | Blocker | A 0-byte re-delivery of a loaded file became its current version and silently emptied it. | Confirmed | Empty files and files without a header are rejected. A readable re-issue with fewer records than an earlier version is still loaded, but the new `file_version_shrink` check raises it. | `test_empty_redelivery_is_rejected_and_a_shrinking_reissue_is_flagged` |
| 4 | Major | Losing the ingest log made the next run delete all of bronze as orphans. | Confirmed | Bronze is never deleted. Every bronze file carries its ingest metadata in the Parquet footer, so a missing log entry is rebuilt from it. A file without metadata is moved to `_orphaned/`. | `test_lost_control_table_is_rebuilt_from_bronze_and_bronze_is_never_deleted` |
| 5 | Major | The explain/review engine was over-engineered: one quarantined record could explain variances on two checks at once, and each rule added in rounds 1–2 had its own edge cases. | Confirmed | **Replaced.** Rows are matched, open or exceptions; nothing is cleared automatically. Quarantined records that might relate are attached to the row as evidence (`candidate_records`, `candidates`) and change no status. The explanation machinery (effect sizes, bounds, subset matching) is gone, and the reconciliation code is about 60 lines shorter even with three new checks. | `test_quarantine_is_evidence_and_never_clears_a_variance` and the adapted round-1/2 tests |
| 6 | Major | The scorecard was still shaped by the generator: defects never overlapped, credit memos always arrived in the same file as the invoice, "open" counted as caught, and the single-batch run hid alarms that fire and later clear. | Confirmed | Defects may now land on the same record. Credit memos arrive up to 10 days later in a later file. Open rows are reported separately from caught ones. The weekly-batch run reports transient exceptions and days to raise. A test checks the published sweep table against a fresh run of one seed. | `test_another_defect_seed_is_handled_as_well`, `test_reconciliation_flags_only_business_errors` |
| 7 | Major | In Spark, `$` matches before a trailing newline, so `"10\n"` parsed as 10 in the Glue job and was rejected in DuckDB. | Confirmed | Spark patterns are anchored with `\A...\z`. The parity fuzzer now includes control characters and trailing newlines. | `test_glue_parity.py` |
| 8 | Major | A stray file in a mis-dated folder (`2026/12/31/notes.txt`) moved the watermark, so every recent variance stopped being "open". | Confirmed | Rejected files do not count towards the watermark. A file whose arrival is before its business date or more than 60 days after it is rejected. | `test_implausible_files_are_rejected_and_do_not_move_the_watermark` |
| 9 | Major | A same-size correction copied with its modification time preserved (`cp -p`, `rsync -t`) was skipped as unchanged. | Confirmed | The skip also compares the file's change time. | `test_same_size_correction_with_preserved_mtime_is_loaded` |
| 10 | Minor | The CLI exited 0 with rejected files and gave no sign of what changed; bank reconciliation keys were line positions that shifted between runs. | Confirmed | Rejected files are printed and the exit status is 3; `--fail-on-new-exceptions` exits 2. Each run records new and cleared exceptions (`recon_changes`). Bank keys are the statement file and line. | `test_cli_exit_codes_signal_rejected_files_and_new_exceptions` |
| 11 | Minor | A quarantined revision 2 counted as released because revision 1 of the same event was in silver. | Confirmed | A record is released only by a load from the same or a newer extract with the same or a higher revision. | `test_quarantined_newer_revision_is_not_released_by_an_older_one` |
| 12 | Minor/nit | A material issue with no shift column passed validation; money accepted misplaced digit grouping (`1,0000.00`); the README said bronze and log were "committed atomically" and that gold SQL runs as Athena views. | Confirmed | Missing shifts and bad grouping are quarantined. The README and design notes now describe the write order and recovery, and say the gold SQL is DuckDB's dialect and would need porting. | `test_missing_shift_and_bad_digit_grouping_are_quarantined` |
| — | Interview point | Same as rounds 1 and 2. | Not a code defect | — | — |

**Also found while fixing:** 18 single-line mutations aimed at this round's rules were run against the suite. 14 were killed by the test written for that rule. Three survived because a test let one rule mask another: the stale-revision test also had an older extract date, so either release condition alone passed it, and the same-day test landed files in an order where ingest sequence agrees with arrival time. Each now has a test where only that rule decides the outcome. The fourth survivor was a real bug: ordering versions of one file name by arrival time made an in-place overwrite with an older timestamp disagree between incremental and full runs. The mutation was the correct code, and it is now the code.
